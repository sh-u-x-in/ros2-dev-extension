time 字段的用途(裁定 2026-10-06):防 pid 复用,永久杜绝杀错进程
上行每帧的 time = 客户端进程启动时刻(恒定,每帧相同);下行每帧的 time = 服务端进程启动时刻。
pid 会被操作系统复用:锁文件/信封里记的 pid,过阵子可能已经顶给了别的进程。
动手 SIGKILL 之前,拿记录的启动时刻和目标进程真实的启动时刻对一下——
对不上 = pid 已经换人,绝不下手。字段本身不花钱。

        }

这个请求就是client心跳,服务端在收到心跳的时候需要响应心跳(裁定:就地秒回——分发层直接应答不进工作池,积压再重也秒回;回应 data 顺带当前负荷),除此之外,还需要额外发送额外心跳

账本按连接记(裁定 2026-10-06):连接断开,服务端只清这条连接自己的账,

  所以识别动作要用 名字后缀 + 类型后缀 双判据(现 classify.ts 即是)。
  srv 类型回 Request 字段树,action 类型回 Goal 字段树。

回答几个问题
我去掉了协议版本,因为插件从未真正发布,没有历史,自然没有协议之说

下行帧(服务端 → 客户端)
下行的全部内容只有两种:一种是"回应"(response,对应上行的某条请求),一种是"主动给"(push,服务端自己看着图变就发)。
回应只发给发起请求的那个客户端;push 广播给所有客户端。其余时间服务端不发废话。

一、回应帧
信封就是上面 success/error 那两个,这里把每种请求的 data 形状补齐:
```json
{
    "service": "<pid>",
    "time": "<服务端启动时刻>",
    "cl-num": <number>,
    "response": {
        "client": "<pid>",
        "id": "<number>",
        "time": "<原样带回请求里的 time>",
        "success": true,
        "data": {...}
    }
}
```
data 按 op 分形状:

resync 的回应 = 全量图快照(节点用全名一列,不再拆 name/namespace 两截;动作不单独列——它就是三条普通服务,客户端自己聚合):
```json
{
    "nodes": ["/talker", "/lc_talker"],
    "topics": {"/chatter": "std_msgs/msg/String"},
    "services": {"/lc_talker/get_state": "lifecycle_msgs/srv/GetState"},
    "lifecycle": ["/lc_talker"]
}
```

ping 的回应 = 负荷快照(就地秒回附带):
```json
{
    "busy": 0.5, "q": [0,1,0,0,0,0], "inf": 2, "brk": 1, "eq": 0, "rss": 48230
}
```

get_param_values 的回应 = 当前值+当前所有被参与轮询的参数 (这条回应是"底账",之后的更新不再走回应,走 push;超限数组以截断标记交付 {"__rde_truncated": true, "total": N, "items": [前1000项]},客户端见标记即知可拿 save 换全值):
```json
{
    "node":{
        "/talker": {"a": 1, "b": "hello", "c/d": [1, 2, 3]},
        "/talker2":["a","b","c/d"]
    },
}
```
把返回具体值的塞进去,因为是等价的,他既然返回了具体的值那么他一定是在轮询,所以的可以等价替换

unget_param_values 的回应 = 当前所有被参与轮询的参数(移出后的账本回显):
```json
{
    "node": {
        "/talker": ["a", "b"],
        "/talker2": ["a"]
    }
}
```

save_param_values 的回应 = 完整值(不截断,按参数名,支持批量):
```json
{
    "/talker": {"c/d": [<全部项>], "e/f": {...}}
}
```

get_form 的回应 = 每个类型一棵字段树(srv→Request 树,action→Goal 树,键=类型串):
```json
{
    "std_msgs/srv/AddTwoInts": [<字段树>],
    "example_interfaces/action/Fibonacci": [<字段树>]
}
```

二、服务端额外心跳(每秒一发)
```json
{
    "service": "<pid>",
    "time": "<服务端启动时刻>",
    "cl-num": <number>,
    "heartbeat": {"busy": 0.5, "q": [0,1,0,0,0,0], "inf": 2, "brk": 1, "eq": 0, "rss": 48230}
}
```
判服务端死活主要靠 socket 断开——进程一死客户端 read 到 EOF,重拉即可;
心跳是看门狗的生命体征(5 秒收不到任何帧 → 杀,杀前用 time 核对 pid 没换人),顺带捎负荷与 cl-num。
我去掉了up,因为up完全可以用time来携带,启动时间减去当前时间不就是up,不需要额外带up

三、主动推送(push)
信封统一,kinds 分四种:
```json
{
    "service": "<pid>",
    "time": "<服务端启动时刻>",
    "cl-num": <number>,
    "push": {
        "kind": "graph",
        "nodes": ["/talker", "/lc_talker"],
        "topics": {"/chatter": "std_msgs/msg/String"},
        "services": {"/lc_talker/get_state": "lifecycle_msgs/srv/GetState"},
        "lifecycle": ["/lc_talker"]
    }
}
```
kind=graph:图一变就推,推全量不推增量——图快照毫秒级、就几十条,全量推省掉两端所有差分/对账的复杂度;节点消失也在这一帧里体现(列表里没了就是没了)。

kind=param:只有计入查询(在册)的参数变了才推(来源是 ROS 原生 /parameter_events,服务端只做账本过滤;截断标记同底账):
```json
{
    "kind": "param",
    "values": {"/talker": {"a": 2}},
    "deleted": {"/talker": ["b"]}
}
```

kind=param_structure:参数名册(名+类型)。这是上行的一个缺口:get_param_values 要点名,但客户端从哪儿知道节点有哪些参数名?名册小、变化少,和生命周期一个待遇——节点出现推一次,名册变了(参数增删)再推一次,客户端永远不请求:
```json
{
    "kind": "param_structure",
    "node": "/talker",
    "params": [{"name": "a", "type": "integer"}]
}
```
(新增参数进名册但**不自动在册**:要不要它的值,客户端展开到它时再订阅)

kind=lifecycle:生命周期节点被认出来推一次,每次转换后再推一次——最后一次永远是对的,前面丢几帧也无所谓:
```json
{
    "kind": "lifecycle",
    "node": "/lc_talker",
    "state": "inactive",
    "states": ["unconfigured", "inactive", "active", "finalized"],
    "edges": [{"label": "configure", "from": "unconfigured", "to": "inactive"}],
    "available": ["activate", "deactivate", "shutdown"]
}
```

四、连接时序(把这些帧串起来)
客户端连上 → 自动发 resync → 服务端回全量图快照(回应帧)→ 紧接着把每个节点的 param_structure、每个生命周期节点的 lifecycle 逐帧推完 → 到此整页可渲染。此后细水长流:只有零星的 push。

五、丢了怎么办
不设 events_lost 这类补丁接口。客户端任何时候觉得数据不对(或者隔一阵子保险起见),重发一条 resync,服务端重推全量——一条原语管一切恢复。

六、不做的事(裁定 2026-10-06)
- 旧版本服务端残留的自愈:只在开发期出现(F5 残留),协议不为它设计;运行期服务端挂死由看门狗兜底。
- 生命周期转换执行不走协议:留在扩展侧 CLI(ros2 lifecycle set)——走 socket 太碍事,socket 只管读不管写。

七、职责划分
服务端(Python,常驻):图/参数名册/在册参数值/生命周期 的数据面;订阅账本(按连接记);ping 就地秒回;rosidl 表单内省。
客户端(TS):连接自愈(connect-first/spawn/看门狗);名字→类型翻译与动作识别(扫类型串);参数树整形;save 落盘;转换执行(CLI)。

八、服务端访问纪律(裁定 2026-10-06)
- _ros2cli_* 终端临时节点不参与:不出现在图里(nodes/services 都滤),不触发任何推送——朝生暮死,是终端命令的影子,追它们的尸体只会白烧超时。
- 助手自身不进图(F5 实测补,2026-10-07):服务名前缀 /rde_param_helper 的条目(自托管参数服务)过滤,观察者效应清场。
- 熔断语义(裁定 2026-10-07"不管了"):失败开断 30s;开断期间该节点一切服务端主动调用(含推送)跳过,**永不自动重试**——没有用户触发就不花任何力气;仅用户再次查询才重新尝试(给满 10s),成功即清账恢复推送;用户不触发则不管。
- 节点串行访问:同一节点任一时刻至多 1 个在途调用,后续同节点请求立即拒绝不排队(推送拒绝=跳过,幂等可重触发)——卡住的节点其一切服务都会卡住,不按节点分类访问就会同时烧 3~4 个线程;单飞后卡死节点最多占 1 个工作线程。生命周期三问随之退串行(并行会被自家第一问的单飞闸门挡住)。
